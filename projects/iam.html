Business purpose

Practice how an organization can structure employee access and apply workstation security requirements, then retain evidence showing what was configured and what still needs testing.

MY WORK / COMPLETED WITH GUIDANCE

From account setup to policy checks.

  1. Established a domain lab: a Windows Server domain controller and domain-joined Windows 11 workstation, supported by an Ubuntu analyst workstation in VMware Workstation.
  2. Organized the directory: created OUs for employees, administrative accounts, groups and workstations; placed the client in the workstation OU.
  3. Provisioned a fictional employee: created an account, assigned employee-group membership and verified domain login and observed session groups.
  4. Configured workstation policy: set a 900-second screen-lock policy and checked the applied GPO, corresponding registry value and HTML computer-policy report.

RESULTS / WHAT THE CHECKS ESTABLISH

Access observed. Policy application checked.

Employee session

The employee group appeared in the observed session groups; Administrators did not. This supports a point-in-time session observation, not a comprehensive effective-access or privilege assessment.

Screen-lock policy

The configuration and application checks supported the 900-second setting. Timed automatic locking was not observed, so runtime effectiveness remains untested.

EVIDENCE / PRIVATE EXPORT PENDING

Document the configuration and the limits.

  • HL-E-001 — Access-verification note: reported saved in the Windows guest; host export and review pending.
  • HL-E-003 — Computer-policy report: reported saved in the guest; host export and redaction review pending.
  • HL-E-007–008 — Directory and policy screenshots: needed to support OU placement, group membership, policy scope and registry checks.

No raw report, credentials, machine identifiers or original filenames are included in this case study.

GRC CONNECTION / LESSONS / NEXT STEPS

Separate intended access from demonstrated control.

Group membership and policy reports help establish configuration. They do not establish every resource permission or prove automatic locking. Next steps are private evidence export/review, a documented timed screen-lock test and further account-lifecycle and resource-permission exercises.

Control objectives include limiting unnecessary access and protecting unattended sessions. No risk severity, verified remediation or regulatory compliance has been established. IAM results do not validate findings or close actions in the separate Sentinel GRC assessment.
